## 一、v1 現在解決得了的問題

### 溝通與資料流
- **舊 Excel 直接可用(day-one)**:讀入現行單機型 Excel,不強迫 PM 改填寫習慣。
- **匯入驗證**:自動回報異常並定位到儲存格 —— 月份標頭 typo(如 `20267'`)、手填區誤植公式(如 summary `T7`)、v2 長表非數值逐格中文訊息。
- **v2 多機型格式**:機型目錄(`HW_SKU`)、各 pool 期初庫存 / 進機 / 退回皆**帶機型 SKU**;工具能從舊資料產生 v2 範本。
- **每月無狀態校準(re-baseline)**:每次匯入即以檔案為唯一事實重新推演,偏差不累積。

### 規劃核心
- **多機型容量推演**:以 vcore 為單位、per 機型維護庫存,逐月回推各 pool 的 in-stock。
- **硬隔離 pool**:fab × BM Group 各自獨立計算,容量不跨池互用。
- **兩種問題都能回答**:
  - **驗證模式**:給定進機計畫 → 各 pool 各月是否可行、缺口多少、標紅。
  - **回推模式**:給定需求 → 建議各月要進什麼機、幾台;可匯出給硬體 team。
- **VM 規格明細裝箱**:部分 product 的不可切割 VM(原子)會做裝箱,能抓出「總量夠但單台裝不下」的情況(內建 NaiveSolver FFD;或委派 CP-SAT)。
- **三種推演模式**:保守(跨月零頭作廢,採購安全邊際)/ 填縫(零頭跨月可用,真實利用率)/ excel_compat(對照舊 Excel 公式,遷移驗證用;黃金測試逐格一致)。
- **配置明細**:顯示哪種 VM → 哪種機型幾台,作為「可行性證明 + 執行參考」。

### 採購 / 退回的 SKU 控制
- **採購限定 SKU(UI 可選)**:回推頁的「機型 catalog(可複選)」可限定本次允許動用哪些機型 —— 例如「今年只能買 A」只勾 A;若某 VM 單台裝不下所選 SKU,會回報「即使補機仍有缺口」。
- **退回帶 SKU**:退回 / 回收的 node 在 Excel Return 區塊指定機型,加回對應 pool。

### 架構
- **可插拔 solver 契約**:`AllocationSolver`(check / suggest),planner / UI 不認實作只認契約。
- **CP-SAT adapter 已備妥**:單維 vcore、原子 VM 委派給同事的 CP-SAT solver、液體 vcore 與採購貪婪留在我方;依賴注入(HTTP / in-process / 測試假後端),已用假後端測到綠燈,可零改動插進 planner。

## 二、v1 目前還解決不了 / 已知限制

### 採購最佳化
- **不做多機型「最佳混搭」**:回推的貪婪法只會挑「單台可售最大」的那一種 SKU 一直買。可以「只買 A」(只勾 A),但無法算「A 買幾台 + B 買幾台」的最省組合。
- **沒有 per-SKU 數量上限**:例如「A 今年最多 5 台,其餘用 B 補」這種約束,目前不支援。
- **沒有成本 / 電力 / 機架 / 交期等維度**:回推只看容量可行性,不做採購成本最佳化。

### 資源維度
- **單維 vcore only**:目前只算 vcore,不含 memory / disk / GPU 多維。(CP-SAT 本身支援多維,但 adapter 現階段只映射 vcore → cpu_cores。)

### Solver 現況
- **CP-SAT 尚未實際接上**:UI 目前跑的是內建 **NaiveSolver(FFD 近似,非最佳)**。要切到 CP-SAT 需先:①同事修好她 solver 的兩個 NameError(`app/server.py` 的 `_SWAGGER_STATIC_DIR`、`app/solver.py::solve()` 的 `needs_two_phase`/`soft_terms` + 缺 `_extract_solution`);②環境裝 ortools。修好後 UI 換一行即可。
- **反親和 / 拓撲 / AG 約束未建模**:CP-SAT 有這些能力,但 v1 容量規劃層沒有用到(僅做容量與裝箱)。

### 配置語意
- **不可搬遷,零頭破碎為近似處理**:已上線機器不可重排,跨月零頭用「保守作廢 / 填縫」兩種近似模式,而非真正的 migration 最佳化。
- **已上線機器的零頭剩餘容量不計**:`Current` 只算完全空置的機台;規劃範圍外在用機器上的零頭 vcore 保守忽略(寧可多備)。

### 使用範圍
- **PM 尚未能線上填需求 / 多人協作**:v1 先自己用,需求仍透過 Excel 進;無帳號權限系統。
- **無歷史版本追蹤**:工具無持久化(這是「每月校準」的刻意設計),但也代表不保留過往規劃版本;要留存請自行保存匯入 / 匯出的 Excel。

## 三、對應你最初的痛點

| 你原本的煩惱 | v1 狀態 |
|---|---|
| 硬體機從單一規格變多種規格,Excel 會很複雜 | ✅ 解決:多機型資料模型 + 裝箱推演,規劃單位從「台數」改成「per SKU + vcore」 |
| 需要工具協助算怎麼分配實體機最合適 | 🟡 部分:內建 FFD 可用;最佳配置待接同事 CP-SAT(adapter 已備妥) |
| 想要有 UI 和 PM 溝通 | ✅ 解決:Streamlit 五頁 UI,可投影對需求;PM 線上填寫為後續 |
| 補缺口時限定某 SKU(今年只能買 A) | ✅ 解決:回推頁 catalog 多選限定採購 SKU |
| 進機計畫 + node 回收一起算 in-stock | ✅ 解決:進機 / 退回皆帶 SKU,逐月回推 per 機型 in-stock |

## 四、之後可補(roadmap 建議)

1. **接上 CP-SAT**:同事修好 solver + 裝 ortools → adapter 換一行切換,拿到最佳配置。
2. **回推支援 per-SKU 數量上限與最佳混搭**:接 CP-SAT 的 suggest 層,或擴充貪婪。
3. **升級多維**:把 memory / disk 帶進需求模型,adapter 映射多維。
4. **反親和 / 拓撲約束**:若容量規劃也要考慮 HA 分散,可引入 CP-SAT 的 AG / topology。
5. **PM 線上填需求、多人協作**:評估 FastAPI + 前端,取代 Excel 進料。
6. **成本 / 交期維度**:採購最佳化不只看容量。
